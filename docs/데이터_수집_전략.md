# 결제 혜택 데이터 수집 전략 (페이 / 통신사)

담당 범위: 페이(카카오페이, 네이버페이, 당근페이, 토스페이 등) 및 통신사 멤버십(SKT, KT, LG U+) 할인 혜택 데이터 수집

---

## 1. 목표

짠돌이 대학생을 위한 앱에서, 사용자가 **어떤 매장에서 어떤 결제수단을 쓰면 가장 이득인지**를 알려주려면 결제수단별 할인 혜택 데이터가 정확하게 구조화되어 있어야 한다. 본 문서는 그 혜택 데이터를 어떻게 수집·관리할지에 대한 전략을 정의한다.

핵심 원칙: **혜택 정보는 자연어(예: "전월 실적 30만원 이상 시 10% 할인, 월 최대 5천원")로 흩어져 있으므로, 계산 가능한 구조화 데이터로 변환하는 것이 수집의 본질이다.**

---

## 2. 현재(MVP) 수집 방식: 수동 큐레이션

### 2.1 왜 수동 큐레이션인가

시연용 MVP 단계에서는 자동 크롤링 대신 **수동 큐레이션**을 채택한다. 근거는 다음과 같다.

- **동적 렌더링 / 로그인 장벽**: 네이버페이·카카오페이 등의 혜택 페이지는 로그인 후 JavaScript로 렌더링되는 경우가 많아, 단순 HTTP 요청 크롤링으로는 데이터를 얻기 어렵다.
- **약관(ToS) 리스크**: 주요 페이·통신사 사이트는 자동 수집을 약관에서 제한하는 경우가 있어, 정식 서비스 전 단계에서 무리하게 크롤링하지 않는다.
- **정확도 우선**: 시연에서 중요한 것은 "데이터가 정확하고 화면에 잘 나오는가"이다. 잘 정리된 수십 건의 검증된 데이터가 불안정한 크롤러보다 시연 효과가 크다.
- **혜택 조건의 비정형성**: 실적 조건·할인 한도·사용 횟수 제한 등은 사람이 읽고 구조화하는 것이 초기에는 더 빠르고 정확하다.

### 2.2 데이터 구조

수집한 데이터는 두 개의 CSV로 관리한다. (UTF-8 BOM으로 저장해 엑셀에서 한글 깨짐 방지)

**(1) `data/benefits_pay_telecom.csv` — 결제수단별 혜택**

| 컬럼 | 설명 |
|------|------|
| benefit_id | 혜택 고유 ID (PAY001, TEL001 …) |
| provider_type | 제공 주체 유형 (pay / telecom) |
| provider_name | 제공 주체명 (카카오페이, SKT 등) |
| payment_method | 결제/적립 수단 (카카오페이 결제, T멤버십 등) |
| category | 매장 카테고리 (편의점 / 음식점 / 카페) |
| merchant_brand | 매장 브랜드 (GS25, 스타벅스 등) — 위치 데이터와 조인 키 |
| discount_type | 할인 방식 (percent / amount / point) |
| discount_value | 할인 값 (숫자) |
| unit | 단위 (% / 원) |
| min_payment | 최소 결제 금액 조건 |
| monthly_cap_krw | 월 최대 할인 한도(원) |
| usage_limit | 사용 횟수 제한 (1일 1회 등) |
| membership_grade | 필요 멤버십 등급 (VIP 등) |
| notes | 조건 상세 / 확인 필요 사항 |
| valid_from / valid_until | 혜택 유효 기간 |
| source_url | 출처 URL |
| verified | 실제 값 검증 여부 (Y/N) |

**(2) `data/stores_location.csv` — 매장 위치 (지도 마커용)**

| 컬럼 | 설명 |
|------|------|
| store_id | 지점 고유 ID |
| merchant_brand | 매장 브랜드 — 혜택 데이터와 조인 키 |
| category | 카테고리 |
| store_name / address | 지점명 / 주소 |
| latitude / longitude | 위도 / 경도 (지도 마커 좌표) |
| notes | 비고 |

### 2.3 두 데이터를 지도에 연결하는 방식

1. 사용자 현재 위치 기준 **반경 500m 내 매장**을 `stores_location.csv`에서 필터링한다. (위도/경도 거리 계산)
2. 각 매장의 `merchant_brand`로 `benefits_pay_telecom.csv`를 조회해 해당 매장에 적용되는 혜택 목록을 가져온다.
3. 카테고리 필터(편의점/음식점/카페)를 적용한다.
4. 지도 마커 위에 해당 매장의 **최대 할인율(또는 대표 혜택)**을 표시한다.

> 페이/통신사 혜택은 보통 브랜드 단위로 적용(예: "카카오페이로 GS25 결제 시 5%")되므로, 혜택은 브랜드 단위로, 위치는 지점 단위로 관리한 뒤 브랜드 키로 매칭하는 구조가 효율적이다.

### 2.4 데이터 검증

현재 CSV의 `verified` 컬럼은 전부 `N`으로 표시되어 있다. 이는 **수치·조건이 예시 기반이며 실제 공식 출처 확인이 필요함**을 의미한다. 시연 전, 각 행의 `source_url`을 통해 실제 혜택 여부·할인율·조건을 확인하고 `verified`를 `Y`로 갱신한다.

## 3. 향후 확장 계획

MVP 이후 데이터의 양과 신선도를 높이기 위해 아래 순서로 자동화를 도입한다. **합법성과 안정성이 높은 소스를 우선**한다.

### 3.1 1순위 — 공식 API / 제휴 데이터
- 페이·통신사가 제공하는 파트너/오픈 API가 있다면 최우선 활용한다. 정확도·안정성·합법성이 모두 가장 높다.
- 프랜차이즈 본사 제휴 정보, 멤버십 공식 페이지의 구조화 데이터를 확인한다.

### 3.2 2순위 — 공공 / 개방 데이터
- 공공데이터포털(data.go.kr) 등에서 활용 가능한 가맹점·상권 데이터를 확인한다.
- 매장 위치 데이터는 지도 서비스 API(카카오맵/네이버지도 로컬 검색)로 지점 좌표를 자동 수집하는 방향을 검토한다.

### 3.3 3순위 — 크롤링 (조건부)
- 위 방법으로 확보되지 않는 프로모션성 혜택에 한해 크롤링을 검토한다.
- 준수 사항:
  - 대상 사이트의 `robots.txt` 및 이용약관 확인
  - 로그인/동적 페이지는 헤드리스 브라우저(Selenium/Playwright) 사용
  - 요청 간격(rate limit) 준수, 서버 부하 최소화
  - 수집 데이터의 출처·수집 시각 기록

### 3.4 데이터 갱신 체계
- 프로모션은 월/주 단위로 변동하므로 **정기 갱신 파이프라인**이 필요하다.
- 향후 AWS 기반으로 확장 시: 예를 들어 스케줄러(EventBridge) → 수집 함수(Lambda) → 저장소(DynamoDB/S3) 형태의 배치 갱신 구조를 검토한다.
- 각 혜택에 `valid_until`을 두어 만료 데이터를 자동 필터링하고, 갱신 시 `verified` 플래그로 검증 상태를 관리한다.

## 4. 요약

| 단계 | 수집 방식 | 상태 |
|------|-----------|------|
| 현재 (MVP/시연) | 수동 큐레이션 (CSV) | 진행 중 |
| 확장 1 | 공식 API / 제휴 데이터 | 계획 |
| 확장 2 | 공공/개방 데이터, 지도 API | 계획 |
| 확장 3 | 크롤링 (약관 준수, 조건부) | 계획 |
| 운영 | 정기 갱신 파이프라인 | 계획 |

MVP에서는 **정확하고 검증된 소량의 구조화 데이터**로 시연 완성도를 확보하고, 이후 합법성·안정성이 높은 소스부터 단계적으로 자동화하여 데이터 규모와 신선도를 확장한다.
